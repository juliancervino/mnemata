# Phase 19.1: Fix content extract problems on web version - Context

**Gathered:** 2026-04-24
**Status:** Ready for planning

<domain>
## Phase Boundary

Address urgent content extraction issues identified in the web client. This includes replacing stubbed-out readability logic with a functional web implementation, fixing browser-only crashes in PDF extraction, and providing manual fallbacks for sites that block automation.

This phase focuses on WEB-05.

</domain>

<decisions>
## Implementation Decisions

### Extraction Engine Strategy
- **D-01:** Implement a client-side readability port on web using JS-interop (wrapping `@mozilla/readability`) to replace the current `readability_platform_stub.dart`.
- **D-02:** Use CORS proxies (e.g., `r.jina.ai`, `allorigins.win`) to fetch raw HTML when direct browser access is blocked, then parse results client-side.
- **D-03:** Refactor `PdfExtractionService` to use web-compatible byte handling, removing all `dart:io` dependencies in the extraction path.

### Dynamic Content & Blocks
- **D-04:** Introduce a **Manual Ingest Mode** affordance that appears when automated extraction fails, allowing users to paste raw HTML or text.
- **D-05:** Provide specific UI feedback/messaging when a site is identified as blocking automated scrapers (e.g., WAF, 403, or 429 errors).

### Claude's Discretion
- **D-06:** Choice of secondary proxy providers and the specific sequence/logic for sequential fallbacks.
- **D-07:** Heuristics for detecting "blocked" states vs "network failure" to trigger specific user messaging.
- **D-08:** Transition timing between automated retry attempts and the presentation of the Manual Ingest path.

</decisions>
