# Phase 19.1: Fix Content Extraction Problems on Web - Research

**Researched:** 2024-05-24
**Domain:** Web Content Extraction & PDF Parsing
**Confidence:** HIGH

## Summary

Web content extraction in Mnemata currently faces three primary blockers:
1. **Stubbed Readability:** The `readability_platform_stub.dart` returns `null` for all web extraction attempts.
2. **CORS Restrictions:** Browsers block direct `http.get` requests to external domains, causing extraction to fail before it even starts.
3. **PDF IO Crashes:** `PdfExtractionService` relies on `dart:io`, which crashes the web runtime.

This research proposes a robust, web-native extraction strategy that avoids "Reader-as-a-service" dependencies like Jina in favor of client-side distillation. By fetching raw HTML via CORS proxies and processing it within the browser's own DOM environment using specialized libraries like `defuddle` (Obsidian's extraction engine) or `@mozilla/readability`, Mnemata can achieve high-fidelity captures while maintaining privacy and control.

**Primary recommendation:** Implement a tiered extraction pipeline using `corsproxy.io` for raw HTML fetching and a JS-interop wrapper for `defuddle` to perform client-side Markdown extraction and metadata parsing.

## Architecture Patterns

### Recommended Extraction Strategy (The "Web-Native" Pipeline)

1. **Fetch Raw HTML via Proxy:**
   - Attempt `corsproxy.io` first (reliable).
   - Fallback to `allorigins.win`.
   - Fallback to `corsproxy.org` or similar.
2. **Initialize Browser DOM:**
   - Use `web.DOMParser().parseFromString(html, 'text/html')` to create a live document in the browser's JS engine.
3. **Metadata Cascade:**
   - **JSON-LD (Schema.org):** Search for `<script type="application/ld+json">`. Parse and look for `@type: Article`, `NewsArticle`, or `BlogPosting`.
   - **Meta Tags:** Extract OpenGraph (`og:title`), Twitter (`twitter:author`), and standard `<meta>` tags.
   - **DOM Heuristics:** Fallback to `h1`, `time` tags, and `byline` detected by the distillation engine.
4. **Content Distillation:**
   - Run `defuddle` on the document. It identifies the "meat" of the page and converts it directly to Markdown, preserving math and callouts.
5. **Output Delivery:**
   - Return a structured `ExtractionResult` to Dart containing `title`, `author`, `publishedDate`, `content` (Markdown), and `siteName`.

### Pattern: JS Interop Wrapper for Defuddle
```dart
// lib/features/ingestion/services/readability_platform_web.dart
import 'dart:js_interop';
import 'package:web/web.dart' as web;

@JS('Defuddle')
extension type Defuddle(web.HTMLDocument doc) {
  external Defuddle(web.HTMLDocument doc, [JSObject? options]);
  external DefuddleResult parse();
}

@JS()
extension type DefuddleResult(JSObject _) {
  external String? get title;
  external String? get content; // Markdown output
  external String? get author;
  external String? get published;
}
```

### Anti-Patterns to Avoid
- **Using Server-Side Readers:** Avoid Jina/Postlight for processing to ensure privacy and offline capability (if possible).
- **Hard-coding Proxy URLs:** Use a tiered list to handle service downtime.
- **Parsing HTML with Regex:** Always use the browser's `DOMParser` for reliability and security.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Readability Heuristics | Custom regex/DOM parser | `defuddle` / `Readability.js` | Handles edge cases (link density, scoring) refined over a decade. |
| Metadata Extraction | Manual tag searching | `defuddle` Metadata Logic | Already implements a robust priority cascade for OG, Twitter, and Schema.org. |
| PDF Parsing | Custom byte parser | `syncfusion_flutter_pdf` | PDF spec is massive and complex; handles font encodings and layouts. |

## Common Pitfalls

### Pitfall 1: Content Security Policy (CSP)
**What goes wrong:** Some proxies might return headers that the browser's CSP blocks when injected into the DOM.
**How to avoid:** Use `DOMParser` which operates in a safe, isolated context, and sanitize if necessary.

### Pitfall 2: Memory Leaks in Browser DOM
**What goes wrong:** Creating many `Document` objects via `DOMParser` without cleanup.
**How to avoid:** Ensure objects are eligible for GC; `DOMParser` documents are typically managed by the JS engine well.

### Pitfall 3: "Please enable JavaScript" Pages
**What goes wrong:** Many modern sites (SPAs) return an empty `div` and a script tag.
**How to avoid:** Simple proxies cannot execute JS. For these sites, "Manual Ingest Mode" or a headless proxy (out of scope) would be needed. This must be communicated to the user.

## Open Questions (RESOLVED)

1. **Should we bundle `defuddle` or `Readability.js`?**
   - **Recommendation:** Use `defuddle` as the primary engine for its superior Markdown/Math support, with `Readability.js` as a fallback or if `defuddle` is too large.
2. **How to handle site-specific extraction (e.g., YouTube)?**
   - **Resolution:** `defuddle` already contains specific extractors for YouTube, Reddit, etc. We should enable these in the options.
