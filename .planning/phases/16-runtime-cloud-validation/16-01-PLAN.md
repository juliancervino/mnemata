# 16-01-PLAN: Human Runtime Cloud Validation Matrix and Evidence Capture

## Objective
Provide a detailed manual testing matrix and evidence capture protocol to validate end-to-end cloud reliability (backup, restore, and scheduler) on real Google account and device environments, fulfilling the requirements for Phase 16 (POR-05, POR-06, POR-07).

## Key Context
The underlying logic for cloud backups to Google Drive, restore payload validation (integrity checks), and the background scheduler (with reason codes) are implemented. Diagnostics are exposed in the Settings UI (Backup Diagnostics tile). The goal of this phase is strictly to execute a matrix of tests in the wild and capture the outcomes.

## Implementation Steps

### 1. Manual Backup Validation Matrix (POR-05)
- **Action:** Trigger a manual Google Drive backup from the settings menu on a real Android/iOS device.
- **Verification:**
  - Verify that the OAuth flow opens, a real Google account can be selected, and authorization succeeds.
  - Verify that the backup completes successfully without errors.
  - Check the Google Drive UI (via web or app) to confirm the backup archive (`.zip`) is present in the app data folder.
  - Check the "Backup Diagnostics" tile in the Settings screen and verify that it displays the successful backup timestamp and any related archive path information.
- **Evidence Required:** Screenshot of the Settings screen showing a successful manual backup and the corresponding file in Google Drive.

### 2. Restore Selection and Apply Flow Validation (POR-06)
- **Action:** Navigate to the restore section in settings.
- **Verification:**
  - Verify that the app successfully lists available backups from Google Drive.
  - Select a valid backup and apply it. Verify the app successfully imports the backup data and the items appear in the main chronological list.
  - **Corruption Path:** (If manually possible) Upload a tampered archive (e.g., incorrect checksum or missing `database.sqlite`) to Google Drive. Attempt to restore it and verify that the restore fails safely with a clear diagnostic message, without corrupting existing app data (all-or-nothing guarantee).
- **Evidence Required:** Screenshot of the successful restore confirmation or list of restored items. Screenshot of the error message when a corrupted archive is attempted.

### 3. Scheduler Runtime Checks Validation (POR-07)
- **Action:** Configure the scheduler policy via settings (e.g., require Wi-Fi, require charging, set a backup interval).
- **Verification:**
  - **Condition 1 (Wi-Fi constraint):** Disable Wi-Fi, trigger the scheduler (e.g., wait or use a dev trigger if available). Verify the "Backup Diagnostics" tile shows failure reason `policy_wifi_required`.
  - **Condition 2 (Charging constraint):** Disconnect charger, trigger scheduler. Verify the "Backup Diagnostics" tile shows failure reason `policy_charging_required`.
  - **Condition 3 (Success path):** Enable Wi-Fi, connect charger, trigger scheduler. Verify a successful background backup completes and updates the last successful backup timestamp.
- **Evidence Required:** Screenshots of the "Backup Diagnostics" tile for each condition (Wi-Fi required, charging required, success).

## Verification & Testing
- Once all matrices are executed, bundle the screenshots and test notes into an evidence directory (`.planning/phases/16-runtime-cloud-validation/evidence/`).
- Verify that every requirement (POR-05, POR-06, POR-07) has corresponding visual or text evidence before closing the phase.
